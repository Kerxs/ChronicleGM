# Chronicle GM 2.0 多人联机：实施报告

按 `docs/mp-review.md` 的 7 个阶段做完。每个阶段都编译通过、有测试，单人模式回归没有退步。代码都没有提交。

## 总体结构

```
玩家客户端 ──wss──▶ Nginx(TLS) ──▶ chronicle-server（单进程 · Rust · SQLite）
                                      ├─ 房间：身份 / 聊天 / 行动队列 / 按权限广播
                                      ├─ 规则引擎（chronicle-core，和单人同一套）
                                      └─ GM Orchestrator ─┬─ 云端模型（OpenAI 兼容，Key 只在服务端）
                                                          └─ /agent ◀──wss── 房主电脑上的 GM Agent ──▶ 本机模型
```

- **权威服务端**：客户端只发意图（行动文字、战斗按钮、聊天）。生命、骰子、物品、NPC、任务都由服务端的规则引擎算好，写进事件日志再广播。伪造的消息类型会被拒绝，多余的字段会被忽略（第 7 阶段的防篡改测试覆盖）。
- **行动处理顺序**：身份验证 → 权限验证 → 状态版本验证 → 行动队列 → GM 理解 → 规则引擎验证 → 数据库事务提交 → 事件广播。
  - 每个行动有唯一的 `action_id`，重启后仍会去重。
  - 被拒绝的行动不推进状态版本。
- **可见性有四档**：公开、个人、指定玩家、只给 GM。
  - 公开事件用白名单，拿不准的一律只给 GM。
  - 私人 GM 对话产生的整段回合只给本人。事件日志只能追加，所以用一条 `mp_scope` 事件记下这段回合的范围，不改旧事件。
  - 快照按玩家过滤：自己的角色卡和背包；队友只有名字、生命和状态。
- **部署形态**：云服务器和房主主机跑的是同一个程序。桌面端用库的方式把服务端内嵌进来。

## 测试结果

- `cargo test --workspace`：**689 个通过，0 个失败**（2.0 之前是 657 个；新增的都是联机测试，其余全部是单人回归）。
- `cargo clippy --workspace --all-targets`：没有警告。
- `npx tsc --noEmit`：通过。`npx vitest run`：**61 个通过**（新增 4 个联机客户端测试）。
- 本地压测（release 版，进程内服务端，脚本 GM）：20 个房间 × 4 人 × 30 秒。
  - 80 个连接，发出 2255 条消息、收到 15382 条，**0 个错误**。
  - 聊天往返平均 1.8 ms，最慢 19.7 ms。
  - 405 个行动完成。
  - Windows 上读不到 RSS；真实服务器（Linux）上的 `/health` 会报告内存。

## 存档兼容

- 单人存档的格式没有变，单人模式的行动者始终是 `party`。
- 联机房间的世界文件和单人存档是同一种格式。新增的只有这几类事件：
  - `mp_action`、`mp_commit`、`mp_scope`、`combat_log`；
  - `party.members` 变量。
- 单人程序打开联机世界不会出错。

## 部署（已完成，2026-11-18）

服务器：Debian 12，2 核，约 1.8 GB 内存，上面已有别的服务（Nginx 的 balatro-3002、ip-access 站点和几个 node 程序），这些都没有改动。

**安装情况**
- 编译：Rust 1.100，在服务器上单线程编译，耗时 133 分钟。
  - 官方源在这台服务器上解析不了，用户同意后改用 rsproxy.cn 镜像。
  - 为编译加了 2GB 的 swap 文件 `/swapfile`，它没有写进 fstab，重启后不会自动挂上。
- 服务：`chronicle-server.service`，开机自启，监听 `127.0.0.1:7788`。
  - 数据目录：`/var/lib/chronicle`。
  - 管理员令牌：`/etc/chronicle/server.env`。
- Nginx：新增独立站点 `chronicle-7780`（`deploy/nginx-chronicle-ip.conf`），对外端口是 **7780**，明文 HTTP，只适合测试。
  - 云服务商安全组已由用户放行 7780。
  - 有了域名后换成 `deploy/nginx-chronicle.conf`，走 HTTPS。
- 外网验证：
  - `http://<服务器地址>:7780/health` 返回正常；
  - 不带令牌建房返回 401；
  - Nginx 的单 IP 连接上限（20）生效。

**真实服务器压测**

| 场景 | 连接 | 消息 | 错误 | 聊天往返 | 服务端内存 | CPU |
|---|---|---|---|---|---|---|
| 外网 → Nginx：10 房 × 4 人 × 60 秒 | 20（另 20 个被单 IP 上限拒绝，符合预期） | 发 1141 / 收 3216 | 0（被拒的连接除外） | 平均 45 ms（公网往返） | 最高 22 MB | — |
| 服务器本机直连：20 房 × 4 人 × 60 秒 | 80 | 发 4500 / 收 20960 | 0 | 平均 0.3 ms，最慢 1.3 ms | 最高约 40 MB | 峰值 9.6% |

- 房间数达到上限 20 时，再建房会被拒绝，上限生效。
- 压测时 GM 没有接入，所以行动都被拒绝。这项测的是连接、聊天、行动队列和广播的承载能力，模型推理不在这台服务器上跑。
- 测试房间都已清理掉，服务现在没有任何房间。

## 已知限制

- 联机战斗目前不调用模型给战斗结果配叙述（单人有 `gm_combat_narrate`）。战斗记录用规则引擎生成的文字。
- 回合进行中如果 GM Agent 断开，这个行动会被拒绝，玩家可以重新提交（auto 模式下会改用云端）。不会在回合中途换节点，避免重复写入。
- 亲手掷骰（`DiceAnswer`）在联机时还是由服务端掷骰。
- 房主主机模式下，外网玩家要连进来需要房主自己做端口转发，或者改用云服务器开房。
- 联机页面通过了类型检查和单元测试，但**还没有在真实的桌面应用里点过一遍**。
