# Chronicle GM 2.0 多人联机：代码审查与最小改造方案（第 0 步）

> 按任务书要求先审查、不动代码。结论基于 2026-11-18 的工作区（含尚未提交的「全面改革」与「试玩修正」）。

## 一、现有结构（实测）

| 模块 | 位置 | 现状 | 多人联机里的角色 |
|---|---|---|---|
| 规则 / 骰子 | `crates/rules`、`core/checks.rs` | 种子骰（ChaCha8，战役种子 + 流号），每次掷骰写事件；`DiceRecord` 带加值明细 | **直接复用**：服务端掷骰，客户端只拿记录做动画 |
| 世界存储 | `core/world.rs`、`db.rs`（rusqlite，世界文件 `.cgw`，迁移到 v14） | 一个世界一个 SQLite 文件，战役、事件、记录都在里面 | **复用为服务端存储**，存档格式与单人完全相同 |
| 事件溯源 / 回溯 | `core/campaign.rs`、`timeline.rs` | 所有修改走 `apply_effects` → 事件日志；每回合检查点 + 重放校验；可从任意检查点开新时间线 | **复用**：断线重连 = 从上次看到的事件序号补发；服务端重启 = 读库即恢复 |
| 状态机 | `core/gamestate.rs`（改革新增） | 设置 / 初始化 / 开场 / 探索 / 等待掷骰 / 战斗 / 战后 / 结局；只有程序能迁移 | **复用**，增加「行动队列」与「状态版本」 |
| 角色 / 背包 / 装备 | `core/rpg.rs`、`pc.rs` | 角色卡、背包、装备都按 **actor 字符串**存（NPC 本来就各有一份）；但玩家固定是 `party`，代码里约 80 处直接写 `PARTY` | **小改**：每个玩家一个 actor（`player:<id>`），把写死的 `PARTY` 改成「当前行动的玩家」 |
| 战斗 | `core/combat.rs` | 网格回合制、先攻、AP、闪避、技能、场景交互；同伴单位已支持多人站位；`players_turn()` 只认 `party` | **小改**：每个玩家单位由各自客户端操作，敌人 AI 不变 |
| AI GM | `crates/gm`（`turn.rs` 1500+ 行） | 模型只提议 JSON 方案，程序校验后执行；NPC 代理、记忆、泄露检查 | **复用**；GM 回合的输入从「一句话」变成「这一轮所有玩家的行动」 |
| 模型接口 | `crates/llm`（阻塞式 `ureq`，OpenAI 兼容）、`runtime` 调度中心 | 本地 / 云端服务配置、Key 存系统凭据、调度优先级 | **复用**：云端 Provider 直接用；本地 Provider 由房主的 GM Agent 调用 |
| 可见性 | `core/spoiler.rs` | 只有一个全局「剧透模式」开关，按「主持人 / 玩家」两级过滤 | **要扩展**成四级：公共 / 个人 / 指定玩家 / GM 隐藏 |
| 桌面端 | `src-tauri`（Tauri 2，命令直接调 core） | 单进程、单用户 | 加「联机客户端」模式：同一套界面，命令改走 WebSocket |

依赖现状：没有直接用 tokio / axum（Tauri 内部带 tokio 运行时）；数据库是 rusqlite（bundled）；HTTP 客户端是 ureq。

## 二、可直接复用 / 需要改 / 需要新增

- **直接复用**：规则引擎、种子骰与骰子记录、事件溯源与检查点、状态机、GM 方案校验（AI 不能写记录）、NPC 记忆与知识隔离、剧本 / 世界树数据、模型服务配置与调度。
- **需要改（小步、保持单人兼容）**：
  1. 「玩家 = `party`」→「玩家 = 一个 actor」：单人模式继续用 `party`，多人用 `player:<id>`。改法是给相关函数加 actor 参数、默认 `party`，不重写。
  2. 可见性四级：事件和记录加 `visibility` 字段（默认公共，旧数据视为公共 / GM 隐藏按原规则），统一在读库、广播、拼 AI 上下文三处过滤。
  3. GM 回合：支持一轮多名玩家的行动（行动队列合并成一次 GM 回合，或按顺序逐个处理）。
  4. 战斗：玩家单位按 actor 区分，轮到谁就只接受谁的操作。
- **需要新增**：
  1. `crates/server`：Tokio + Axum + WebSocket 的权威服务端（房间、身份、行动队列、状态版本、广播、断线重连、健康检查、内存监控、限流）。云服务器和房主主机跑**同一个程序**。
  2. `crates/protocol`：客户端 ↔ 服务端、服务端 ↔ GM Agent 的消息定义（serde，带版本号）。
  3. GM Orchestrator + 两种 Provider：`Cloud`（服务端直接调云端 API，Key 只存在服务端）、`Local`（房主的 GM Agent 主动连上服务端领任务，再调房主本机模型，结果回传；本机模型端口不暴露到公网）。
  4. 桌面端联机界面：创建 / 加入房间、公共聊天、私聊、私人 GM 对话、玩家列表与连接状态。

## 三、兼容性方案

- **存档**：服务端就用现有世界文件格式。新增字段都带默认值，新增表走现有迁移机制（v15 起）。单人存档能直接被服务端打开，多人存档在单人模式里也能打开（只看到 `party` 的视角）。
- **单人模式**：不经过服务端，照旧直接调 core。所有改动保证现有 657 项 Rust 测试、57 项界面测试继续通过，每阶段都跑全量回归。
- **数据库选型**：任务书写的是 SQLx，但现有存档、迁移、事件溯源全建立在 rusqlite 上。任务书同时要求云服务器和房主主机共用同一套存档格式，所以建议**服务端继续用 rusqlite**（放在 `spawn_blocking` 里执行，每个房间一个写连接），不引入 SQLx。见第五节的决定 2。

## 四、分阶段计划（每阶段：编译 + 相关测试 + 单人回归 + 存档兼容检查 + 文档 + 修改清单）

| 阶段 | 内容 |
|---|---|
| 1 多人基础设施 | `crates/protocol`、`crates/server` 骨架（Axum + WebSocket + 健康检查 + 内存监控 + 限流 + 日志轮转）；core 的 actor 参数化（单人默认 `party`） |
| 2 房间 / 身份 / 权限 / 通信 | 房间（2–4 人可配置）、加入码 + 会话令牌、断线重连；公共聊天、私聊、私人 GM 对话；四级可见性过滤 |
| 3 统一状态与事件 | 每房间行动队列、`action_id` 去重、状态版本校验、事务提交后广播、按序号补发、定期快照 |
| 4 AI GM 双模式 | GM Orchestrator；Cloud Provider；GM Agent（Local Provider，主动加密连接、心跳、任务超时与重派）；本地 / 云端 / 手动切换；同一房间只有一个权威 GM 节点 |
| 5 多人规则与战斗 | 多人 GM 回合；多人战斗（各自操作自己的单位，结果服务端算、广播一致） |
| 6 云 / 房主双模式 | 同一服务端程序：Debian 部署（systemd + Nginx 反代 WebSocket + TLS）、房主模式（桌面端内嵌启动服务端，局域网 / 直连），中继留接口不实现 |
| 7 测试 / 部署 / 性能 | 4 人联机端到端、断线 / 重启恢复、篡改测试（客户端伪造骰子 / HP 被拒）、2 核 2GB 压力测试、文档 |

## 五、需要你决定的

1. 现在工作区里有「全面改革」和「试玩修正」两大批未提交的改动。2.0 改动面很大，建议先提交一个检查点再开工（提交需要你同意）。
2. 数据库：建议服务端沿用 rusqlite，以保证存档格式与单人一致，而不是任务书写的 SQLx。
3. 推进方式：7 个阶段像上次一样自动做完再统一确认，还是每阶段停下确认。
4. 压力测试环境：验收要求在 2 核 2GB 的 Debian 12 上实测。你是否有这样一台服务器可以让我 SSH 部署？没有的话，我可以在本机用 WSL / Docker 限制 2 核 2GB 模拟，但那不算真机实测。
