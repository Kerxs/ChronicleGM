### AI 请求方式
- 只有一种客户端：OpenAI 兼容接口（ureq，同步阻塞调用）。支持流式输出、取消、自动重试、日志脱敏、单次请求关闭思考，以及 JSON schema 约束输出。
- 调用点只有两处：
  - `gen/runner.rs`：生成任务，后台线程执行，全局排队、一次一个。
  - `gm/ask.rs`：GM 回合，前台调用，**不排队**。
- 每个任务可以分别指定模型服务（世界生成、GM 叙述、NPC、摘要等）。软件不预设任何默认模型。

### LLM / TTS / ASR 的管理方式
- **LLM**：按之前的约定，模型由用户自己准备，软件只负责识别：探测本机端口和 `/v1/models`、`/props`，并能只读解析 GGUF 文件。软件**不启动、不停止、不加载、不释放**任何模型。
- **TTS**：能识别出 Breeze TTS 服务存在，但**没有任何语音合成功能**。
- **ASR**：**没有**。
- 任务书第 9 条要求"与现有语音系统兼容"，但项目里目前**没有语音系统**，需要从零新建。

## 2. 已有功能清单
- **世界树**：17 种节点类型；懒加载的虚拟化树；搜索；拖拽排序；回收站；版本快照；导入导出（带格式版本号）；一致性检查；关系与关系图（以某个节点为中心的邻域图，最多显示 300 个节点）。
- **剧本**：AI 分段生成（先大纲后章节）、只重生成选中条目、继续扩展、规模表、人物表。
- **剧情图**：有向图编辑器；条件和效果用 DSL 表示，由程序求值；结构检查；模拟运行；试玩；AI 生成整图、生成分支、一键补全死路。
- **AI 写入控制**：AI 的产出都要经过变更集、校验、审阅台，用户确认后才写入；所有写入都有修订记录，可撤销、可重做。
- **AI 主持（GM）**：
  - AI 只提方案，检定、效果、剧情跳转都由程序执行；
  - NPC 代理只知道自己该知道的信息，每回合最多 2 个 NPC 开口；
  - 有泄露检查，以及"GM 替 NPC 说话"的转交机制；
  - 战役记忆：要记住的事实、会话摘要（需用户确认）、NPC 记忆；
  - 核心设定受保护，AI 不能修改。
- **战役状态**：
  - 变量、任务、线索、物品、关系、实体状态，都存在战役自己的覆盖表里，不改动世界设定；
  - 事件日志只能追加（数据库触发器保证）；
  - 骰子使用 ChaCha8 随机数生成器，"战役种子 + 流号"决定结果，可以复现。
- **加固**：
  - 自动备份并轮换、从备份还原；
  - 完整性检查和安全修复；
  - 崩溃恢复：中断的生成任务、中断的回合；
  - 启动失败时显示原因页面；错误日志会轮换；
  - NSIS 安装包。

- CPU：Ryzen 9 7845HX（12 核 24 线程）
- 内存：31.8 GB
- 显卡：RTX 4070 Laptop，8 GB 显存
- 系统：Windows 11
- 模型：Ornith-1.5-35B-Q4_K_M（20.2 GB）
- 推理服务：llama-server b12063，按你的 `启动.bat` 参数启动：`-c 32768 -ngl auto`，KV 缓存 q8

- 界面内存只测了约 2 分钟。**2 小时长时间运行未测**，要等 Phase 1 有了监控之后再测。
- **未测**：LLM 和 TTS 交替运行（没有 TTS 功能），模型多次启停（软件目前不管理模型进程）。

## 4. 当前性能瓶颈（按影响排序）
1. **大模型推理本身**。每个回合的时间几乎全花在模型上，程序侧的耗时是毫秒级。优化重点应该是：减少请求次数、压缩上下文、让前台请求优先。
2. **没有统一调度**：
   - GM 回合不排队，生成任务和 GM 回合会同时打到同一个模型服务；
   - llama-server 有 4 个槽位，同时处理时会平分速度，在共用 KV 缓存时还会挤占上下文；
   - 后台生成会直接拖慢前台 GM 回复。
   
   目前没有优先级、暂停、去重，也不检查资源。
3. **显存和内存几乎用满**：显存 7.7/8.2 GB，系统内存只剩 7.6 GB。语音模型很难和 LLM 同时放进显存，需要做到：语音跑在 CPU 上，或者和 LLM 分时运行（需要软件能控制模型的加载和释放）。
4. **"在场 NPC"判断太粗**：现在把剧本里所有人物都算作在场（最多 8 个）。实测中出现过 NPC 声称自己在根本没去的地方。NPC 数量增加后，这会同时影响上下文长度和剧情一致性。
5. **剧情图编辑器会渲染全部节点**（没有只渲染可见区域）。1000 个节点仍然流畅，但内存会随节点数增长。关系图上限 300 个节点，表现良好。
6. **AI 请求是同步阻塞调用**：每个请求占一个系统线程。现在并发很少，问题不大；接入统一调度后会改成由调度器管理的工作线程。

## 6. 数据库迁移方案（只是方案，还没执行）
- 沿用现有机制：每个迁移追加一个 SQL 文件；迁移前自动备份；每个迁移在自己的事务里执行，失败就回滚；数据库版本高于程序时拒绝打开。每个迁移都配一个"从旧版本升级"的测试。
- **世界库**：
  - v6：时间线。在 `campaigns` 表上加 `parent_campaign_id`、`fork_seq`、`status`（进行中/已结束/归档）、`ended_at`；新增 `campaign_snapshots` 表（战役编号、事件序号、快照文件、校验和、程序版本）。
  - v7：战役内人物关系 `campaign_relations`（a、b、视角方、强度、信任、好感、敌意、来源事件序号）和关系变化历史。
  - v8：NPC 状态，包括位置、日程、情绪，以及情绪变化的来源事件。
  - 后续：世界时间和环境、地图和探索、势力，战斗和物品扩展，每块各一个迁移。
- **资料库**：
  - v3：模型托管配置（可执行文件路径、启动参数、端口、角色是 LLM/TTS/ASR）、任务队列持久化、性能采样。
- 已有存档：只新增表和列，不修改、不删除已有数据。旧战役默认为"进行中"，没有父时间线。

## 7. 风险
1. **范围非常大**。任务书 8 个阶段里，单独任何一个的工作量都接近之前整个 Phase 2–5。我会按阶段逐个实施，每个阶段结束都停下来等你确认。
2. **模型托管与之前的约定冲突**：Phase 1 要求"按需加载和释放、动态调整 GPU Offload、模型异常恢复"，这些都需要软件能启动和停止模型进程。而之前的约定是"软件不启动模型"。另外，llama-server 运行中能否调整 GPU Offload，**我还没有验证**，不做假设；目前已知能确定可行的办法只有：改参数后重启模型进程。
3. **显存只有 8 GB**，LLM 加 TTS 很难同时放进 GPU，"同时运行"多半只能做成"分时运行"或"语音放在 CPU 上"。
4. **回溯依赖程序版本**：规则引擎以后修改的话，重放旧事件可能得到不同的结果。应对：以快照为主，事件重放为辅；快照里记录程序版本；校验时比对重放结果和快照，发现不一致就提示。
5. **本地模型的能力**：剧情导演、证据链分析这类开放任务对模型要求高，效果要靠真实试玩来验证；做法仍然是程序为主，AI 只提建议。
6. **硬件监控覆盖面**：显存只能在 NVIDIA 显卡上通过 nvidia-smi 读取；AMD 和 Intel 显卡先标注"不支持"，不编造数据。

## 8. 测试方案
- 每个阶段都有：单元测试、集成测试（用模拟模型，明确标注）、真实模型联调（用你的 llama-server，测完关闭）、发布版端到端走查。
- **性能**：
  - 规模基准扩展到"N 个 NPC × M 条事件"，验证 NPC 增多时请求数不会线性上涨；
  - 用图谱渲染脚本（`perf.mjs`）测更大的图；
  - 调度器压力测试：一边跑后台任务一边测 GM 首字延迟；
  - 2 小时长时间运行，每分钟采样内存。
- **回溯**：
  - 随机战役 → 结束 → 在任意节点分叉 → 比对状态，覆盖第五节列出的全部字段；
  - 原时间线的字节级校验；
  - 多次连续回溯。
- **异常**：运行中强制结束进程、模型进程崩溃、数据库损坏，分别验证能否恢复。

## 9. 需要你确认
1. **软件是否接管模型进程**（影响 Phase 1 的范围）。
   - 建议：新增可选的"托管模式"。用户自己填写 llama-server、TTS、ASR 的程序路径和启动参数，软件按这些参数启动、停止、重启，并在崩溃后恢复。
   - 默认仍然是"只识别"。
   - 软件不下载模型，也不替你选择或更换模型。
2. **语音功能从零新建**。先接 Breeze TTS（它的 HTTP 接口要先实测，不做假设）。ASR 用哪个服务由你来定（没有默认）。
3. 阶段顺序按任务书执行（P1 → P8），每个阶段结束后停下等你确认。
