# Phase 7：AI 剧情导演和 GM 控制台 · 完成报告

日期：2026-11-13。按任务书第十节实施。

## 设计要点
- **程序算节奏，模型出主意**：
  - 紧张度、停滞、重复、可用的剧情钩子、剧情冲突全部由程序计算，不调用模型。
  - 只有需要"出主意"时才请导演模型分析：停滞、重复、例行间隔，或主持人手动请求。
- **导演只提建议**：
  - 建议存为战役记录，主持人采用后才进入 GM 的上下文。停滞时可以自动采用第一条，可以关闭。
  - 导演自己不执行任何效果。
- **不阻塞 GM 回复**：自动分析在 GM 回合结束后才在后台发起，优先级 P3。调度中心规定后台任务不会在前台（GM、NPC）有请求时开始。
- **严格区分主持人信息与玩家信息**：
  - 控制台只在主持人视角显示，切回玩家视角会自动离开控制台。
  - 导演指引只进入 GM 的上下文，并加入泄露检查；NPC 的上下文里没有。
  - 后台分析完成的提示只在主持人视角显示。
- **兼容现有系统**：
  - 新数据都是战役记录（`director_note`、`director_beat`）、受保护变量（`director.settings`）或事件（`context_trace`、`conflict`、`manual_edit`），随时间线回溯。
  - 时间线比较时跳过导演的内部记录。
  - **没有新增数据库迁移**。

## 对照任务书

| 要求 | 实现 |
|---|---|
| 观察玩家行动 | 每回合记录节拍：紧张度，以及这一回合的进展（线索、任务、剧情推进、物品、地点、战斗、新情报）。比较最近三次行动的相似度，判断是否在重复 |
| 分析当前世界状态 | 紧张度由程序根据战斗、玩家生命、任务期限、人物情绪、天气计算并说明原因。导演分析时拿到完整的 GM 上下文（含主持人信息）、节奏、剧情钩子、最近的游戏记录 |
| 控制悬念和剧情节奏 | 导演给出节奏判断：raise（提高紧张、推动事情发生）/ hold / release（放缓、给玩家喘息）。这个判断进入 GM 的上下文 |
| 生成合理的剧情转折 | 建议分为提示、麻烦、转折、人物主动行动、事件、节奏；每条写明理由和依据的事实（编号由程序换成原文）。提示词要求与已有事实一致，优先使用已有的钩子 |
| 检测剧情停滞 | 连续 N 回合（默认 4，可设置）没有进展判为停滞（战斗中不算）；玩家重复同样的行动也会提示。两者都会在回合结束后触发后台分析，同一次停滞只分析一次 |
| 不强迫玩家选择 | 导演和 GM 的提示词都写明：建议是可以提供的机会，玩家不接也没关系，不能写成"让玩家必须……" |
| 不擅自修改已确认设定 | 已确认设定（核心正典与状态为已确认的世界节点）列给导演，禁止改写。<br>模型自报 `touches_canon`、或建议同时提到已确认设定的名称和"其实、原来、并非、推翻"等词时，标为需要主持人确认，不自动采用。<br>导演不写数据；GM 的效果仍然经过原有的校验（核心设定不可改） |
| 当前场景 | 剧情节点（含主持人信息）、地点、在场人物、可选分支（条件此刻是否满足、是否走过、条件原文） |
| 世界状态和时间 | 时间、季节、天气、玩家位置、全部变量 |
| NPC 目标、情绪和状态 | 每个人物的定位、目标（剧本动机与人物资料）、秘密、此刻的活动与地点、存活状态、等级与生命、五项情绪、对玩家的关系、是否在场 |
| 隐藏剧情 | 剧本的核心设定与真相、还没到达的剧情节点及主持人信息、未开始的隐藏任务 |
| 线索和触发条件 | 每条线索是否揭示及真相；所有触发器、任务的开始、完成、失败条件，此刻是否满足、是否已经发生 |
| AI 记忆检索记录 | 每回合记录：上下文各部分的放入情况和 token；检索到的战役记忆（M1…）和世界设定（W1…）；采用中的导演建议；每个 NPC 回应时检索到的记忆 |
| 剧情冲突提示 | 死亡人物仍被任务需要、剧情走进死胡同、玩家倒下、叙述可能泄露主持人信息、叙述与程序结算不符（新增的启发式检查）、GM 的修改被拒绝 |
| 手动修改游戏状态 | 效果编辑器可以修改任何战役状态，必须写明原因。写入事件日志：可以回溯、参与重放校验，控制台保留修改记录 |
| 查看 AI 决策引用的历史事实 | GM 方案新增 `based_on`：这一回合的决定依据了哪些记忆、设定或剧本内容（编号由程序换成原文、不认识的编号忽略）。控制台按回合显示：玩家的话、GM 意图、依据、检索记录、被拒绝的修改、冲突、叙述 |

### 真实联调（你的 llama-server，托管模式，共 2 轮）
场景：
- "钥匙失窃"：村长在酒馆等人帮忙，铁匠是窃贼。剧本只有一个开场节点（用来检查死胡同提示）。

- 导演设置：3 回合没有进展算停滞，不做例行分析。

**第 1 轮**（玩家前 3 回合只是喝酒发呆）：

| 观察 | 结果 |
|---|---|
| 停滞检测 | 第 3 回合后：已经 3 回合没有进展，判为停滞；钩子包括未揭示的线索、未开始的任务、没打过交道的铁匠 |
| 后台分析 | 回合结束后自动发起，11 秒后给出建议；第一条自动采用：让村长坐到玩家桌边把话说完，并顺嘴提到"铁匠阿岩最近神神秘秘" |

### 联调中发现并修复的问题
1. **导演的判断只写了一个词**（第 1 轮写成了"stall"）：现在不像句子时用程序算的节奏说明代替，提示词也给出了示例。
2. **建议文字里带编号**（"……埋线（依据 M3、M2）"）：现在会去掉，依据单独显示。
3. **建议类型五花八门**（npc_enters、new_clue、deadline……）：现在归到固定的六类，提示词也限定了取值。
4. **谈出关键信息仍被判为停滞**（第 1 轮控制台显示"已经 6 回合没有剧情进展"，但村长已经交代了失窃经过）：GM 记下的新情报和任务的新情况现在也算进展。
5. 已加回归测试。

## 已知问题和尚未完成的部分
1. **后台分析与下一回合可能同时请求模型**：
   - 后台任务不会在 GM 请求排队或进行时开始，但已经在进行的导演请求不会被中断。
   - 玩家在导演分析的十几秒内就输入下一句时，两者会同时占用你的模型服务，GM 回复会变慢（不会出错）。
   - 本次联调没有出现重叠。
2. **建议质量取决于模型**：偶尔夹杂英文（第 1 轮出现过"players"），也可能把人名和编号连在一起（"村长老格村长"）。
3. **叙述与结算不符的检查是启发式的**：只覆盖倒下和"全部没命中却写命中"两种情况。
4. **"已确认设定"的改写检查是关键词式的**：换了说法的改写挡不住。不过导演本身不写数据，GM 的效果仍然受核心设定保护。
5. **控制台的手动修改只针对战役状态**：不能直接改世界树正典（这是有意的，世界树在世界树页编辑）。
6. **导演不会主动安排剧情分支或生成新的剧情节点**：只提建议；需要新内容时仍然走原有的"动态节点、新实体、审阅"流程。
