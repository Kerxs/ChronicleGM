## 二、压测中发现并修复的问题

| 问题 | 怎么发现的 | 修复 | 验证 |
|---|---|---|---|
| **软件被强行结束时，托管的模型进程变成孤儿进程**，继续占着端口和约 7 GB 显存；重启后软件只能把它们当成"外部服务"，无法停止、重启或切换 | 读代码发现 `Drop` 在强杀时不执行；写测试复现：宿主进程被 `TerminateProcess` 后，模型进程仍在响应 | 模型进程放进 Windows 作业对象（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`），本软件的进程句柄一关闭（包括强杀、崩溃），系统随即结束作业里的全部进程 | 新测试 `managed_models_die_when_host_process_is_killed` 修复前失败、修复后通过；真实联调中强杀应用，llama 与 Breeze 在 2.4 秒内被系统结束，无残留 |
| **另一个程序打开存档时写入失败**（"database is locked"） | 并发压测：另一线程反复打开存档时，500 次写入失败 30 次 | 写事务改为一开始就取得写锁（`TransactionBehavior::Immediate`）。默认的延迟事务先读后写，升级写锁时 SQLite 直接报错而不等待 | 同一压测 5000 次写入 0 失败；全部测试通过 |
| **NPC 越多，GM 提示词越长**（"不在场的人物"把所有人列出来） | NPC 数量压测：1000 个 NPC 时提示词多出约 7300 字 | 最多列 20 人（有日程或已死亡的优先），其余只给人数 | 50 → 1000 个 NPC 提示词都是 14,731–14,732 字 |
| **性能中心"本程序内存"把托管模型子进程也算进去**（显示 22 GB） | 冒烟运行的资源采样 | 本程序的进程树去掉模型进程后再统计 | 修复后长测中本程序显示 63–116 MB |

### 长测发现：这台机器上 LLM 与 TTS 同时常驻时物理内存不足

- **现象**：按你的启动参数，llama-server 常驻约 27.6 GB 私有内存，并随提示词缓存涨到 34 GB；加上 Breeze 的约 5 GB，超过了 32 GB 物理内存。
- **影响**：Breeze 几乎全部被换出到页面文件，工作集只剩 50–90 MB。第 3–9 回合语音的实时率掉到约 10，一段 21 秒的旁白要合成 2–4 分钟；那 1 次语音超时也发生在这段时间。
- **对照实验**（`phase8-start-order-ab.txt`）：排除了"启动顺序"这个原因。"一起启动"与"Breeze 运行中只重启 llama"两种方式各测 2 次，固定提示词的输出都是 19.5–19.6 tok/s，显存都约 7.7 GB。
- **重启后的变化**：前 40 分钟的低速（llama 输出中位 11.3 tok/s）在第一次重启 llama 后消失（之后 33–34 tok/s，语音实时率中位 1.47）。重启释放了 llama 增长的内存，这与内存压力的解释一致，但没有做更细的单独验证。
- **处理**：这是硬件容量与模型参数的问题，按约定**没有改动你的模型参数**。可选的缓解方向由你决定：
  - 去掉用不到的 `--mmproj`（本软件不发图片）；
  - 用 llama-server 的 `--cache-ram` 限制提示词缓存；
  - 减小 `-c`；
  - 或在性能中心给 llama 设置定时重启（长测中每 40 分钟重启一次，每次约 26 秒）。

## 已知问题

1. **这台机器上 LLM 与 TTS 同时常驻会内存不足**（第四节）：语音会明显变慢，偶尔超时。软件侧行为正确（超时报错、不影响 GM 回合），根本解决需要调整模型参数或硬件，由你决定。
2. **导出文件随回合数线性增大**：每回合一个完整状态检查点，5000 回合的战役导出 44 MB，导入约 1.3 秒。日常规模（几百回合）在 2 MB 以内。
3. **世界图谱页在本次界面测试中没有收到渲染耗时上报**：人物关系页有上报。交互帧率已实测，但缺少这一页的渲染耗时数字，原因没有查。
4. **编年史没有"模型润色"**：当前是确定性生成，没有做调用模型改写成叙事文的可选功能。
5. **全文搜索走 `LIKE` 全扫描**：3 万条事件、无结果时 11 ms；规模再大十倍后可能需要事件全文索引（要加数据库迁移，本阶段没有做）。
6. 本地模型偶尔在叙述中夹英文单词（长测中出现过 "Exchange"、关系类型 "friend"）。导演的英文检查会提示主持人，程序不自动改写。
