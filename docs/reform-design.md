# Chronicle GM 全面改革：现状对照与设计（第 0 阶段）

> 这是动工前的设计文档：先把现有功能和新需求一一对上，找出最小改造方案，再定状态机、数据结构和分阶段计划。
> 原则：复用现有 Rust 规则引擎与事件日志，不重写；所有新状态都走事件日志 → 自动支持存档、回溯、中途退出恢复。

## 一、现有架构速览

| 层 | 位置 | 现状 |
|---|---|---|
| 规则 / 骰子 | `crates/rules`（骰子表达式、`SeededDice`）、`crates/core/src/checks.rs` | D20 + 修正，成功等级五档，优势 / 劣势，骰池；每次掷骰写事件 `roll`（战役种子 + 流号，可复现）；本轮已支持玩家亲手掷骰 |
| 属性 / 技能 | `crates/core/src/rpg.rs` | 角色卡（属性、技能、HP、状态、伤势）、`check_modifier` = 属性修正 + 技能 + 装备加值（正是需求里的公式）；属性方案随剧本 |
| 战斗 | `crates/core/src/combat.rs`（969 行） | 回合制、先攻 1d20+敏捷、行动点、10×6 网格、射程、掩体、状态效果、士气、首领、逃跑、弹药、奖励；战斗存为战役记录，**已经支持中途退出恢复** |
| 状态 / 存档 | `crates/core/src/campaign.rs`、`timeline.rs` | 事件溯源；每回合检查点；从任意节点开新时间线 |
| AI GM | `crates/gm/src/turn.rs` | 模型只提议（方案 JSON），程序校验后执行；检定、战斗、交易、物品全部由程序结算 |
| 后台任务 | `crates/runtime`（调度中心 P0–P5） | 模型 / TTS 请求统一排队、可取消 |
| 界面 | `ui/src/App.tsx` + 14 个页面 | 侧栏应用式外壳；游戏页 = 剧情区 + 玻璃球 `GmOrb` + 右侧 11 个页签；骰子是 2D 演出 `DiceShow` |

**结论**：需求第六～八条（规则引擎、骰子、AI 与规则分离、持久化）大部分已经具备；缺的是 ① 统一的游戏状态机，② 初始化流程，③ 游戏化的主界面 / 游戏空间 / 战斗场景，④ 战斗里的闪避、技能、场景交互，⑤ 3D 骰子与"所有骰子都可视化"。

## 三、游戏状态机

后端 `crates/core/src/gamestate.rs`。状态是战役记录 `game_state`（随时间线回溯），每次迁移写事件 `game_state`。

```
            ┌──────────┐ game_init 开始  ┌──────────────┐ 7 步全部完成  ┌─────────┐ 开场回合结束
 (新战役) ─▶│  setup   │───────────────▶│ initializing │──────────────▶│ opening │──────────────┐
            └──────────┘                 └──────────────┘                └─────────┘              ▼
                                           ▲ 失败可重试                                     ┌───────────┐
                                                                                            │ exploring │◀──────┐
           ┌─────────┐  玩家掷骰 / 跳过  ┌──────────────┐  回合中提出检定且选了亲手掷骰      └───────────┘       │
           │exploring│◀─────────────────│ awaiting_dice │◀──────────────────────────── │  │                    │
           └─────────┘                   └──────────────┘                                │  │ 程序开战            │
                                                                                         │  ▼                    │
                                  ┌──────────────────── combat ───────────────────────┐ │                       │
                                  │ intro（转场）→ player_turn ⇄ resolving ⇄ npc_turn │─┘ 胜 / 败 / 撤退 → aftermath ┘
                                  └───────────────────────────────────────────────────┘
                                                     任意状态 ──结局──▶ ended（只能回溯开新时间线）
```

- **谁能迁移**：只有程序（`gamestate::transition`）。合法迁移表写死在代码里，非法迁移返回错误并写日志；模型方案只能"请求"（开战、结束战斗由战斗引擎判定）。
- **和现有逻辑的关系**：`combat.active` 变量、`OPENING`、亲手掷骰等待，统一由状态机记录；`combat.rs` 结算结果驱动 `player_turn / npc_turn / aftermath`。
- **界面**：只读状态机（`game_state` 命令 + `game-state` 事件）决定显示大厅 / 初始化 / 游戏空间 / 战斗场景，不再由界面自己猜。
- **恢复**：打开战役时读 `game_state`：在 `combat` 就直接进战斗场景（战斗记录本来就有），在 `awaiting_dice` 回到"轮到你掷骰"，在 `initializing` 从未完成的那一步继续。

### 主要数据结构（Rust，经 ts-rs 导出给界面）

```rust
pub enum Phase { Setup, Initializing, Opening, Exploring, AwaitingDice, Combat, Aftermath, Ended }
pub enum CombatPhase { Intro, PlayerTurn, Resolving, NpcTurn }
pub struct GameState { phase: Phase, combat: Option<CombatPhase>, init: InitProgress, since_turn: i64, updated_at: i64 }
pub struct InitProgress { steps: Vec<InitStep> }            // 7 步，各自 pending / running / done / failed + 说明
pub struct DiceRecord {                                     // 每一次掷骰（检定、攻击、伤害、先攻……）
    purpose: String,       // attack / dodge / damage / initiative / check:<技能> / effect:<状态>
    expr: String, dice: Vec<i64>, kept: Vec<usize>,
    parts: Vec<(String, i64)>,   // 「属性 敏捷 +2」「技能 射击 +3」「掩体 −2」……
    total: i64, target: Option<i64>, outcome: String, stream: i64, manual: bool,
}
```

## 四、初始化流程（真实后台任务）

`game_init(world, campaign)` 在后台线程逐步执行，每步推送 `game-init` 事件（步骤、状态、耗时、说明），进度条只按完成的步骤走，**没有假进度**：

1. 加载剧本：读剧本、章节、剧情节点，跑 `script_check`（结构问题提示，不阻塞）。
2. 加载世界设定：读核心设定索引（世界库 v5 的索引），准备地点、势力。
3. 初始化玩家角色：`pc::set`、生成角色卡、发放初始装备（没有装备时调用模型推断，属真实 AI 任务）。
4. 初始化 NPC：为剧本出场人物建立角色卡与情绪初值（已有的不重复）。
5. 初始化人物关系：从剧本 / 世界树建立关系网络（`network.rs`）。
6. 构建 AI GM 上下文：真实调用 `context::build`，预热提示词缓存（向模型服务发一次很短的请求，失败不阻塞并说明）。
7. 检查世界数据和存档：完整性检查（`integrity.rs`）、写第一个检查点。

每步幂等（重复执行不会多发装备、不会重复建卡）；任何一步失败停在那一步，界面给出"重试 / 跳过（可跳过的步骤）/ 返回"。

## 五、战斗系统改造（在 `combat.rs` 上扩展）

- **掷骰可视化**：`roll()` 改为返回 `DiceRecord`，`CombatReport` 增加 `dice: Vec<DiceRecord>`；攻击检定、闪避检定、伤害骰、先攻、状态效果全部有记录。
- **新行动**：`dodge`（花 1 行动点，到下次轮到自己前，被攻击时掷 1d20+速度 对抗攻击总值）、`skill`（技能动作：规则里的 `custom_actions` + 按属性的通用技能，如"瞄准射击 +2 命中"）、`interact`（战场物件：程序随场景生成 1–3 个，例如「货箱：躲到后面获得掩体」「油灯：打翻点燃一格」）。
- **速度**：派生属性，先攻与移动格数都参考它。
- **AI 的角色**：开战与否由程序根据方案判定；战斗中 AI 只负责每轮的描述（结算之后写）。玩家的行动可以点按钮，也可以说话（"我躲到货箱后面" → 识别成 `interact`，由程序校验）。
